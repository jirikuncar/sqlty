## Stub Generation (`.pyi` overload signatures)

Generate `.pyi` stub files with `@overload` signatures for configured database functions. Functions registered via `[[tool.sqlty.functions]]` in `pyproject.toml` — no decorator needed.

### Deferred CLI

```
sqlty generate .           # Analyze source, emit .pyi stubs
sqlty generate --check .   # Exit 1 if stubs are out of date
sqlty clean .              # Delete generated .pyi files
```

## ty oracle for row types

For the `TypedDict` and `NamedTuple` cases of `tests/mdtest/check/static_resolution.md`,
a test could generate `def f(x: <column type>) -> <annotation>: return x` and check that
ty reports `invalid-return-type` exactly where sqlty reports `column-type-mismatch`. ty is
already a dev dependency. Pydantic lax mode, the `int` -> `float` promotion and NULL
handling are known differences to exclude.

## Engine Gaps

- **SQLite free-form type names.** SQLite accepts any type name and derives an
  affinity (sqlite.org/datatype3.html section 3.1), but `UNSIGNED BIG INT`,
  `VARYING CHARACTER(255)`, `NATIVE CHARACTER(70)` or `anything goes` make
  sqlty skip the table silently. A follow-up could map such columns by the
  affinity rules (contains `INT` -> `int`; `CHAR`/`CLOB`/`TEXT` -> `str`;
  `REAL`/`FLOA`/`DOUB` -> `float`) and warn when a schema table is skipped.
- **Other dialects.** Dialects beyond PostgreSQL, MySQL and SQLite use
  sqlparser-rs's parser with a handful of canonical type names; they have no
  mdtest suite of their own.
- **Two type tables.** SQL -> Python types live in Rust's `SQL_TO_PYTHON_TYPE`
  and, as runtime types for row type checks, in `_type_extractor.py`.

## Left over from shipped plans

- **`# sqlty: ignore[...]` quick fix** in the server; it must not land inside a string.
- **`redundant-optional` across files** in the server.
- **A breaking baseline ref that moves** while the server runs; today only a saved schema
  or config re-resolves it.
- **Unsaved buffers**: should a check resolve helpers and row types of other unsaved
  buffers, or the files on disk only?
- **Notebooks**: queries in cells (LSP 3.17 notebook sync).
- **Files that lose their types**: surrogate escapes and files over 256 KiB. Decoding
  string escapes in Rust and a parse stack sized by nesting rather than length would lift
  both.
- **`.sql` query files**: protocol stubs and `SQL[T].file(...)`.
- **Receivers of helper methods** (`receivers.rs`, `flow.rs`, `modules.rs`):
  - Classes are compared by `(module, name)`, so a class defined in a function or in
    another class is skipped rather than followed. Interning classes as ids would lift
    that, and splitting the resolver into an extractor of declarations, a resolver that
    knows no syntax tree and a table of special forms per language would let it type
    other languages' receivers.
  - Not followed, though a type checker follows them: the result of an unannotated
    function, a union whose classes reach helpers that take the call in different ways
    (check the call against each), `isinstance` with a
    tuple or on a name of an unrelated class, `type(x) is C`, `match` class patterns,
    `TypeGuard`, the type arguments of a generic class.
  - The decorators, defaults and annotations of a `def` are read in its own scope, not
    the one around it: a name the function binds is read there as the function's.
  - The header of a class nested in a class that binds the name only after it: the name
    is not bound there yet and is the module's, but it is read as the outer class's and
    left unknown, so a call on it is not checked.
  - Row types are still found by `Tree` among the checked modules only; `Modules`
    reads stubs and libraries for helpers and receivers, not yet for a row type a library
    defines.
  - The playground (`sqlty-wasm`) checks one file with no helper index: helpers of other
    modules and stubs are not read there.
  - A stub is read for helpers when a checked file or a read stub names its package. A
    stubbed package named only by a library that is neither checked nor stubbed is not.
  - A `sqlty breaking` snapshot keeps the stubs its files name, not the library modules
    a receiver's class was read from, nor those `functions` are defined in.
  - Language server: a symlinked directory below a root, reported by the path it
    resolves to, does not drop what was read through the link (a root or a `stub-paths`
    directory that is a link does).
  - Language server: with a client that watches statically and only its folders, a
    stub or library outside them is read again on every edit rather than kept. The
    server registers the outside directories only with a client that takes dynamic
    registration and relative patterns.
  - Which stubs are read for helpers is decided by a pass over the text of every checked
    module per index build; the server could keep the packages each module names.
