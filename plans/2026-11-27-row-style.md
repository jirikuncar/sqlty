# Named row types from rewrite

Tracks [#1354](https://github.com/jirikuncar/sqlty/issues/1354).

## Goal

`row-style` lets `rewrite` and `check --fix` write a named row class instead of
`SQL[tuple[...]]`, so code reads fields by name. The class is named after the variable the
query is assigned to (`GET_USER` and `get_user` give `GetUserRow`), written below a
`# sqlty: generated` line after the imports, as `json-types` and `param-types` write theirs,
and removed by `strip`. When the query changes, `check --fix` rewrites the class's fields and
keeps its name.

sqlc-gen-python makes the same choice per project: dataclasses by default,
`emit_pydantic_models` for `pydantic.BaseModel`
([README](https://github.com/sqlc-dev/sqlc-gen-python/blob/main/README.md)).

## Setting

| `row-style` | Class |
|-------------|-------|
| `"tuple"` (default) | none: `SQL[tuple[...]]` as today |
| `"namedtuple"` | `class GetUserRow(typing.NamedTuple)` |
| `"typeddict"` | `class GetUserRow(typing.TypedDict)` |
| `"dataclass"` | `@dataclasses.dataclass` `class GetUserRow` |
| `"pydantic"` | `class GetUserRow(pydantic.BaseModel)` |

## Examples

`tests/mdtest/rewrite/row_style.md`:

```python
GET_USER = "--sql\nSELECT id, name, email FROM users WHERE id = %s"
# rewritten-file: import typing
# rewritten-file: from sqlty import SQL
# rewritten-file:
# rewritten-file:
# rewritten-file: # sqlty: generated
# rewritten-file: class GetUserRow(typing.NamedTuple):
# rewritten-file:     id: int
# rewritten-file:     name: str
# rewritten-file:     email: str | None
# rewritten-file:
# rewritten-file:
# rewritten-file: GET_USER = SQL[GetUserRow]("--sql\nSELECT id, name, email FROM users WHERE id = %s")
```

One section per style (`dataclass` imports `dataclasses`, `pydantic` imports `pydantic`),
plus these cases:

- Keeps `tuple`: a query not assigned to a name (`execute(conn, "--sql\n...")`); a column
  that is not a valid field name (`count(*)` gives `count`, valid; `?column?`, `1`,
  `class`, `_id` for `namedtuple`, duplicates); a query with no rows.
- Names: `get_user` and `GET_USER` give `GetUserRow`; a taken name gets `GetUserRow2`, as
  JSON classes do; two queries with the same columns still get one class each.
- A JSON column of known shape with `json-types = "typing.TypedDict"` is a field typed by
  its generated `TypedDict`.
- With `param-types`, `SQL[GetUserRow, tuple[int | None]]`.
- `# stripped:` removes every generated row class (the decorator of `dataclass` too), so
  `strip(rewrite(x)) == x` holds and `test_core_invariants.py` covers each style.
- `# fixed:` after the query gains `created_at` and drops `email`: the class has `id`,
  `name`, `created_at`, still `GetUserRow`. A hand-written class (no marker) is never
  rewritten: the `column-*` rules report it as today.

## Hosts

The class is written where `json-types` classes are: `sqlty-project` `module::typed` (CLI,
`sqlty server`), `sqlty.core._typed` (Python API) and the wasm playground's `params` step,
each calling one `sqlty_python::rows::add_row_types`. VS Code reads the setting through the
server. `check` gains no new path; `--fix` reruns the pass.

## Budget

`rewrite` and `check --fix` only: one `analyze_select` per call the pass rewrites, as
`json-types` does; `check` without `--fix` is unchanged. Measured with
`benchmarks/ab.py` (and the `rewrite` metric of `bench-ci`), with `row-style` off and on.

## PRs

1. Setting, the four styles, `strip`, docs (`configuration.md`, the psycopg and asyncpg
   guides, whose helpers build each class).
2. `check --fix` updates a generated class when its query changes, keeping the name.
3. `check` reports a named row type on a call that returns tuples (`cursor.execute`, asyncpg's
   own `fetch`), for generated and hand-written classes alike.

## Out of scope

- Reusing a table class when a query selects all of a table's columns.
- `msgspec`, `attrs` and other class kinds.

## Risks

- A generated class name may shadow a later definition: names already bound in the module are
  skipped (`GetUserRow2`).
- Pydantic validates on construction, so an inferred type that is too narrow fails at
  runtime where a tuple would not. `narrow-type` already reports those annotations.

## Open questions

1. Where is a class written?
   - a. Every query assigned to a name; PR 3 reports one run through a call that returns
     tuples. (Recommended: queries are often defined in one module and run in another,
     where `rewrite` cannot see the call.)
   - b. Only where the module shows the query passed to a `sqlty.drivers` helper.
2. Spell the values as the issue does (`"namedtuple"`) or as `json-types` does
   (`"typing.NamedTuple"`, `"dataclasses.dataclass"`, `"pydantic.BaseModel"`)?
   Recommended: as the issue does; they are short and need no module.
3. `dataclass` with `frozen=True`? Recommended: no, as sqlc-gen-python writes
   `@dataclasses.dataclass()`.
